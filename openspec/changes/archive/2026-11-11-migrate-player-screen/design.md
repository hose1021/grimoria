# Design

## Context

See `proposal.md` - Why. State that shapes the approach:

- `Shell` resolves a route key, then renders either a native screen or
  `LegacyBridge`, which calls `mount(root)` and acquires the writer lock.
- `ShellPorts` exposes the router, the game source, roles, strings, locale,
  assets and preferences. It has no command port: `/sheet` and `/public` are
  read-only.
- `js/player.js` renders four things: the setup message, the number grid, the
  timed role card and the hand-back modal. Its timer stores an absolute deadline
  and recomputes the remaining time on every tick.
- `js/store.js` still accepts the legacy command shape; `store.dispatch` is the
  only mutation path.

## Goals / Non-Goals

**Goals:**

- The handoff becomes a shell screen with the same look, URL and storage keys.
- The claim goes through a port; no `src/ui` module imports `js/`.
- The picker follows the store subscription.
- One writer-busy card, shared with the bridge.

**Non-Goals:**

- Changing the 45-second value, the claim rules or the player projection.
- Preflight, legacy CSS removal or a second token source.
- Migrating `/bag`, `/seat`, `/secrets` or `/table`.

## Decisions

**A narrow command port instead of a general dispatch port.** `claimSeat` is the
only command `/player` may send. A port shaped
`commands: { claimSeat(playerId, name): DispatchResult }` keeps command
composition in the composition root, where the legacy command shape and the
typed store meet. A general `dispatch(CommandInput)` would let the UI build any
command and would need a cast at the `js/store.js` boundary.

**`writer` moves out of `legacy`.** The lock is not a bridge detail: the handoff
needs it too. `writer: { acquire(): Promise<boolean> }` is used by the bridge and
the player screen, and the busy card becomes `WriterBusy`.

**The deadline lives in a ref.** The card stores `deadline` as an absolute
timestamp when the number is tapped; the interval recomputes the remaining time
from it. A `setInterval` that decrements a counter would drift and would restart
on every render. The effect keys on the selected seat, so a store publish does
not restart it.

**The hand-back modal is the Radix `Dialog`.** It already provides the focus
trap, Escape, focus restore, `aria-modal` and the accessible name. The dialog
gains an optional `footer` so the screen can render the confirm control and a
cancel control that is still a `Dialog.Close`; `DialogClose` is exported for
that. The legacy markup was a hand-rolled equivalent.

**Class names stay.** `.player-view`, `.player-numbers`, `.player-card`,
`.player-role-name`, `.player-save`, `#player-name` and `data-seat` remain as
inert hooks. The browser checks and the visual contract depend on them, and the
utilities are unchanged.

**The picker subscribes to the store.** This is the one observable difference:
the legacy screen rendered once per event, so an external publish left it stale.
The shell subscription costs nothing and matches the other native screens.

## Risks / Trade-offs

- **Writer lock on a native route.** The bridge acquired it; a native screen must
  acquire it too, or two tabs could claim the same seat. The screen renders the
  same busy card until the lock is granted.
- **Timer and the Playwright clock.** The interval must keep reading `Date.now()`
  so `page.clock.fastForward` hides the card; a counter decrement would pass the
  local clock but change behavior in a paused tab.
- **Dialog markup change.** The warning loses its decorative `warning` label and
  gains Radix defaults. Focus, Escape and `aria-modal` keep their contract.
- **Deletion.** `js/player.js` disappears in the same change; the worker asset
  list and the bundle are regenerated by the build, and a leftover import would
  fail the build.
