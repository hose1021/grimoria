# Rules matrix

Audited on 2026-11-10 for the supported ruleset. This document is the
implementation baseline for issue #19: it records what the engine automates,
what stays a Storyteller decision, what is untested, and what is unsupported.
It is not a rules authority by itself: a `verified` row cites a permanent wiki
revision and at least one named test; the other rows record their status. Every
row with a supported status carries exactly one rule identifier in its first
column: a role identifier for a role row, and a `SYS-` identifier for a
cross-cutting row declared in `docs/rules-shared.md`. The durable behavior
contract derived from the `verified` rows lives in `openspec/specs/`; this matrix
stays the audit table for `host-choice`, `implemented-unverified` and
`unsupported` cases. `docs/role-ownership.md` is the generated role-by-role
ownership view: module declarations, coordinator references and the rule
identifiers below.

## Follow-up audit on 2026-11-15

The source/test comparison that issue #199 asked for is recorded here, not in a
separate audit file. It compared the pinned text with the engine and the named
tests for the roles #199 named, and repaired four evidence drifts without
changing a rule:

- **Chambermaid.** The dedicated wake-count, wake-prerequisite and target tests
  now back the row as `BMR-CHAMBERMAID-01..03`; only the impaired false number
  stays `host-choice`.
- **Assassin.** Decline, later use, second use, impairment, an unknown target,
  a duplicate completion and resurrection are asserted as `BMR-ASSASSIN-02`.
  The pinned text (r1786) says declining does not spend the ability and the How
  to Run section spends it only when a player is chosen; Professor r1775 says a
  resurrected player regains a used once-per-game ability.
- **Evil Twin.** The "good cannot win while both twins live" branch is asserted
  as `SNV-EVILTWIN-02` (r3101).
- **Empath.** The count is verified with numeric, dead-neighbour and
  registration tests; registration and false information stay explicit
  `host-choice` rows (r1724).

A passing provenance check or test suite does not re-audit every `verified`
row. Remaining review tasks are listed under "Unknown and unverified rules".

### Evidence dimensions

Each row carries the four dimensions issue #200 asks for, in its columns:

| Dimension | Column | Values |
| --- | --- | --- |
| Implementation | Engine behavior | absent (no row) / partial / implemented |
| Execution | Host decision | automated (empty) / required host decision |
| Evidence | Test | named asserting test / none, and the pinned revision in the role cell |
| Interaction | Jinx table and interaction tests | tested / host-resolved / unsupported |

The public support level stays one of `verified`, `requires-storyteller-choice`
or `unsupported`, derived from the rows: any `host-choice`,
`implemented-unverified` or `unsupported` row weakens the role. The README and
the `/bag` and `/secrets` screens render that one derived model.

## Status legend

| Status                   | Meaning                                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `verified`               | The official text is pinned, the engine implements every behavior named in the row, and at least one listed test asserts it.                        |
| `implemented-unverified` | The engine has code or a step for the mechanic, but no test asserts it, or the test covers only part of it.                                         |
| `host-choice`            | The official text leaves the decision to the Storyteller. The app creates a step and stores the input, but does not resolve the rule automatically. |
| `unsupported`            | The mechanic is not modeled. The host must resolve it outside the engine, and the app must not present it as automated.                             |

A row marked `host-choice` or `unsupported` is not a defect by itself: the
issue requires the app to expose only legal options and to mark manual
resolution. It becomes a defect when the app claims automation it does not
have, or when it offers no legal host control.

### Unknown and unverified rules

- Every active Cerenovus and Mutant madness condition has a separate review
  keyed to its effect; `endDay` is blocked until all are decided. Whether a
  player was mad stays a Storyteller judgement.
- Pit-Hag, Barber, Snake Charmer and Philosopher character changes are limited to the tested paths; arbitrary corrections are not applied.
- Vortox false information and impaired information are host-supplied: the engine requires a host answer instead of presenting the computed truth, but the lie itself is the Storyteller's.
- Pukka self-target is a legal choice (r3074 How to Run: "They point at any
  player"). The pinned text does not define what happens to the previous
  victim's pending death while the Pukka is poisoned by itself: the engine
  suspends that death and resumes it when the Pukka is healthy, which is an
  extrapolation. The engine applies this as its default reading, the step note
  states it, and `BMR-PUKKA-06` is `host-choice`: the Storyteller records a
  different reading with the correction dialog (mark the death, deactivate the
  poison, or clear the winner), which journals the reason.
- The Chambermaid count, the Assassin's once-per-game lifecycle and the Evil
  Twin both-live block are asserted; see the 2026-11-15 follow-up above.
- A Sailor or Innkeeper drunk recipient is chosen in the step sheet and limited
  to the legal players; the engine rejects a third player
  (`error.drunk-recipient`). A direct engine call can omit the choice, which the
  UI never does (`BMR-SAILOR-01`, `BMR-INNKEEPER-01`).
- The Artist answer under a living Vortox stays a host answer: the question is
  free-form, so the engine cannot compute a false answer (`SNV-ARTIST-01`).
- The Dreamer's character pair and the Sage's two-player pair are host-shown and
  not stored by a dedicated control (`SNV-DREAMER-01`, `SNV-SAGE-01`).
- The Pukka self-target resume interaction is a host-adjudicated default
  (`BMR-PUKKA-06`).
- Registration after death is asserted for the Recluse and Spy lookup; other registration-dependent queries remain review tasks.
- Jinx pairs among the supported characters are pinned in the versioned table;
  the app lists the pair and the Storyteller resolves it, so no jinx is claimed
  as automated.

## Update procedure

1. Fetch every pinned revision with `node scripts/fetch-official.ts`; it writes
   `docs/official/wiki/` and records it in `docs/official/manifest.json`. Run
   `node scripts/fetch-official.ts --check` to list the pages whose latest
   revision moved.
2. Compare the revision ids with the per-row links. A changed revision needs a
   rules review, not an automatic update.
3. Update the row, its rule identifier, its source link and its test in the same
   change. A cross-cutting row also updates its declaration in
   `docs/rules-shared.md`, and a new identifier is unique and permanent.
4. Never mix a new revision with the pinned `docs/official` snapshot in one
   game. The snapshot is the engine data; the wiki revision is the rule claim.
5. Run `npm test` and the affected route before reporting.
